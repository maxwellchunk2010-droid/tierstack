Ship safely: a security checklist for AI-built apps

Before you put real users or customer data on an app you built with an AI tool, run through this list. It covers database access, secrets, spending limits, logged-out testing, and one hosting setup-link caution. Sources were checked 2026-11-17.

Editorial checklist, not a penetration test. This is a plain-English pre-ship list, not a hands-on audit of any one app or vendor. Paying never changes a rank, and nobody paid to be mentioned here.

Turn on Supabase Row Level Security

If your app uses Supabase, Row Level Security (RLS) is the rule layer that decides which rows each database role can read or change. Supabase’s publishable (anon) key is designed to be public, so access control depends on RLS being enabled and on policies that are not overly broad (for example, a policy that allows anonymous reads of everything).

Official Supabase docs warn that a table in an exposed schema without RLS can be readable and writable by any role with a grant on it. Their advice: enable RLS on every table in an exposed schema, set grants to match what the app actually needs, write a policy per operation, and test allow and deny cases for signed-out and signed-in roles.

  • Enable RLS on every table that the client can reach.
  • Write policies tied to the signed-in user where data should be private.
  • Revoke leftover default grants that are broader than your app needs.
  • Use Supabase’s security advisor in the dashboard to flag tables with RLS turned off.

What the Lovable exposure research found

In November 2026, German security firm Crissy Field GmbH published research (covered with Handelsblatt on Nov 2, with updated figures in the research report) on apps built with Lovable.

  • They examined 159,041 Lovable projects from the open web archive Common Crawl (December 2025 to September 2026).
  • Of those, 34,545 used Supabase.
  • 24,664 of those sites sent database records as soon as the page loaded, with no login. The researchers are clear that this alone is not automatically a leak: some of that data may be intended for public display.
  • With further read-only requests using the same public API key, they found records containing email addresses in 10,560 tables across 7,403 of those 24,664 sites. They also documented serious exposures, including personal profiles, payment information, and identity-document details. They note that the 30% figure is not a confirmed leak rate, and that the Common Crawl sample is not representative of all Lovable apps.

This was not a hack of Lovable itself. The findings point to missing or over-permissive Row Level Security in the generated apps. Access-control mistakes can happen in any stack. If you built on Lovable and Supabase, turn on RLS and test while logged out before you ship, then check again after permission changes. See the Patch Notes entry and our AI app builder guide.

Watch API keys that have no spending limit

A secret that can call a paid API is also a blank check if it leaks and the account has no cap. Before you ship:

  • Set a billing limit, spend cap, or budget alert on each provider key you use (OpenAI, Anthropic, Google, and any other billed API). Check the vendor’s official billing or usage settings for how to do that.
  • Give each environment its own key, and revoke keys you no longer need.
  • If a key may have been committed to a public repo, pasted into a chat, or baked into a client bundle, rotate it and review the bill.

Keep secrets out of client code

Anything shipped to the browser, baked into a mobile app, or committed to a public repository can be copied. Keep service-role keys, private API keys, webhook secrets, and database admin credentials on the server or in environment variables that are not published with the app.

A special case: the Supabase publishable (anon) key is meant to be public. That is not a license to skip access control. The key can appear in client code by design, which is why RLS and tight policies have to decide what a signed-out visitor can read. Never put the Supabase service_role key in client code; it bypasses RLS.

Test while logged out

Build tools and preview windows often keep you signed in, so a page can look fine to you and still be open to a stranger. Before you ship, and again after you change permissions:

  • Open the live URL in a private or logged-out window, on a browser that has no session cookie for your app.
  • Confirm that private records, admin screens, invoices, messages, and account lists are not visible.
  • Try the actions a signed-out visitor should not be able to run (edits, exports, payments, user lookups) and confirm they fail.
  • If you use Supabase, confirm that tables you consider private are not readable with only the public anon key.

If anything private appears, turn on or tighten RLS (or the equivalent access rules on your stack) before you add real customer data.

Treat a Spacefast setup link like an admin credential

Spacefast, launched by Automattic on Nov 9, 2026, is a hosting and deploy layer for apps built with tools such as Claude Code, Codex or Cursor. It is watch-listed and unranked on TierStack; see the Patch Notes entry.

A TechTimes hands-on published Nov 10, 2026 (reporter Devin Culbertson, citing tester Casey Burridge) reported that redeeming the setup link can give the agent admin rights over the team through an API key, so the link behaves like an admin credential. The same review said the link itself expires shortly after it is created, while the resulting API key can last longer.

Treat that setup link the way you would treat a password: do not paste it into a public chat, a ticket, or a shared doc, and do not leave it in a screenshot. This is one tester’s published finding, not a TierStack hands-on test; confirm current behavior in Spacefast’s own docs before you rely on it.

FAQ

Were Lovable apps hacked?

No. Research published by Crissy Field GmbH found many Lovable projects using Supabase returned database records without a login. Sending records on page load is not automatically a leak, because some data may be meant to be public; the researchers also found further readable records, including serious exposures, on a subset of those sites.

How should I test an AI-built app while logged out?

Open the live site in a private or logged-out browser window, as a stranger would. Confirm that private records, admin pages and account data are not visible, and that actions meant for signed-in users fail. Do this before you put real customer data in the app, and again after you change permissions.

No. Keep service-role keys, private API keys and other secrets on the server or in environment variables that are not shipped to the browser or committed to a public repo. A publishable Supabase anon key may appear in client code by design; that is why RLS and tight policies have to do the access control.
